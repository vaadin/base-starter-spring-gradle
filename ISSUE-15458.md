# Issue 15458 — vaadinBuildFrontend irregularly failing with ZipException

<https://github.com/vaadin/flow/issues/15458>

## Root cause

`FrontendDependencies.visitClass()` resolves class resources through a
`URLClassLoader` created by `ReflectionsClassFinder`. For classes located
inside jar files (e.g. sibling module jars in a multi-module Gradle project),
`url.openStream()` goes through `JarURLConnection`, which uses `JarFileFactory`
— a **JVM-global static cache** (`sun.net.www.protocol.jar.JarFileFactory`).

In the Gradle daemon the JVM persists across builds. The `URLClassLoader`
created by `ReflectionsClassFinder` is **never explicitly closed**, so its
cached `JarFile` handles linger in `JarFileFactory`. When Gradle recompiles a
sibling module and rewrites its jar in-place, the stale cached `JarFile` has a
central directory pointing to offsets in the **old** file content. Reading at
those offsets from the **rewritten** file yields garbage, causing:

```
Visiting class com.example.lib.SharedComponent failed with
  ZipFile invalid LOC header (bad signature).
  This might be a broken class in the project.
```

or the variant:

```
Visiting class com.example.lib.SharedComponent failed with
  Unexpected end of ZLIB input stream.
  This might be a broken class in the project.
```

## Why it is intermittent

The bug depends on GC timing. If the JVM garbage-collects the old
`URLClassLoader` between builds, the stale `JarFile` is closed and evicted from
the `JarFileFactory` cache — and the next build opens a fresh one successfully.
Rapid successive builds reduce the chance of GC running in between, increasing
the reproduction rate.

## Why single-module projects are unaffected

In a single-module project the user's classes live in `build/classes/java/main/`
(a **directory**). The `URLClassLoader` reads `.class` files directly from the
filesystem — no `ZipFile` is involved. Dependency jars from the Gradle cache are
immutable and never change between builds. Therefore there is no stale jar to
produce a `ZipException`.

All reporters in the issue have multi-module projects, code-generation plugins
that output jars, or concurrent IDE builds — all cases where a jar on the
classpath gets rewritten between daemon runs.

## Required conditions

| Condition | Why |
|---|---|
| Multi-module project (or code-generation plugin producing jars) | User classes must be in **jar files** on the classpath, not directories |
| Gradle daemon enabled (2nd+ run) | `JarFileFactory` static cache must be populated from a prior run |
| Source changes in sibling module between runs | Triggers jar rewrite, making the cached `JarFile` stale |
| GC has not collected the old `URLClassLoader` | Keeps the stale `JarFile` alive in the cache |

## Code path

1. `GradlePluginAdapter.createClassFinderClasspath()` assembles the classpath.
   For sibling project dependencies it includes their **jar artifacts**
   (resolved through `dependencyConfiguration.incoming.artifactView`).

2. `BuildFrontendUtil.getClassFinder()` wraps these paths in a
   `ReflectionsClassFinder` backed by a `new URLClassLoader(urls, contextClassLoader)`.

3. `FrontendDependencies.visitClass()` calls
   `getFinder().getResource(className.replace(".", "/") + ".class")` which
   returns a `jar:file:.../lib.jar!/com/example/lib/SharedComponent.class` URL.

4. `url.openStream()` → `JarURLConnection` → `JarFileFactory.get(url)` returns
   the **stale cached `JarFile`** from a prior build.

5. The stale `JarFile`'s central directory offsets no longer match the rewritten
   file content → `ZipException`.

## Reproducer setup

The reproducer converts the single-module starter into a two-module project so
that a sibling module's jar ends up on the Vaadin classpath scanner.

### Project structure

```
base-starter-spring-gradle/
├── settings.gradle          # includes 'lib'
├── build.gradle             # depends on project(':lib')
├── lib/
│   ├── build.gradle         # plain java library with vaadin-core
│   └── src/main/java/com/example/lib/
│       └── SharedComponent.java   # @NpmPackage-annotated Vaadin component
├── src/main/java/com/example/demo/
│   └── MainView.java        # uses SharedComponent from lib
├── reproduce.sh             # sequential reproducer
└── reproduce-concurrent.sh  # concurrent reproducer (simulates IDE + CLI)
```

### Running the reproducer

#### Sequential (stale JarFile cache)

```bash
./reproduce.sh
```

This script:

1. Stops any existing Gradle daemon (clean slate).
2. Runs an initial `clean vaadinBuildFrontend` (warms up the daemon and
   populates the `JarFileFactory` cache).
3. Loops up to 50 times: modifies `SharedComponent.java`, rebuilds.
   Each iteration rewrites `lib.jar`. If the stale `JarFile` from the previous
   iteration is still in the cache (old `URLClassLoader` not yet GC'd), the
   scan fails.

Successfully reproduced on attempt 11 with:

```
Visiting class com.example.lib.SharedComponent failed with
  Unexpected end of ZLIB input stream.
  This might be a broken class in the project.
```

#### Concurrent (simulates IDE + CLI)

```bash
./reproduce-concurrent.sh
```

This script:

1. Starts a background loop that continuously recompiles `lib` and rewrites
   its jar every 0.5 s (simulating an IDE triggering Gradle in the background).
2. Runs `vaadinBuildFrontend` in the foreground repeatedly.
3. The race between the jar being rewritten and the frontend scanner reading it
   produces the `ZipException`.

### Tips to increase reproduction rate

- **Increase heap** to reduce GC pressure (stale `URLClassLoader` survives
  longer): add `org.gradle.jvmargs=-Xmx4g` to `gradle.properties`.
- **Disable explicit GC**: add `-XX:+DisableExplicitGC` to the jvmargs above.
- **Run builds in rapid succession** — the scripts already do this.

## Possible fixes

1. **Close the `URLClassLoader`** in `ReflectionsClassFinder` after scanning is
   complete (or make it `AutoCloseable` and close it in the Gradle task). This
   would release `JarFile` handles and evict them from `JarFileFactory`.

2. **Disable `URLConnection` caching** before opening streams:
   ```java
   URLConnection conn = url.openConnection();
   conn.setUseCaches(false);
   InputStream is = conn.getInputStream();
   ```

3. **Read class bytes from the `Reflections` scan results** rather than
   re-opening class files through `URLClassLoader.getResource()` +
   `url.openStream()`.
